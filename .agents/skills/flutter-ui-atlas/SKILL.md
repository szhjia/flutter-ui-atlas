# Flutter UI Atlas

Use Atlas to build a desktop map of an app's real screens and transitions. Work from the target Flutter project, keeping its existing entry point, widgets, routing, and development workflow.

## Connect an app

- Locate the Flutter project by its `pubspec.yaml`. Check `atlas --version` and `atlas --help` for the installed CLI. If it is missing, follow the source installation instructions at https://github.com/szhjia/flutter-ui-atlas.
- Establish the app's running Web URL and inspect its actual routes and accessible content in a browser. Atlas connects to that URL; it never runs Flutter commands, builds the app, or starts its server. Starting or rebuilding the app is a separate step using the app's own tools and the user's authorized scope.
- Run `atlas init --url <running-url> --ready-text "<exact visible entry text>"` in the project. Omit `--ready-text` only when a pending candidate is intended. If `.atlas/atlas.yaml` already exists, preserve it rather than reinitializing.
- Run `atlas config` to set the app URL, authentication, and accounts. With `--no-open`, use the local URL printed by the command. For form authentication, use the login page's exact username/password labels, submit button, and success/failure checks. Test the configured accounts.

No Atlas SDK, special Flutter entry point, scene parameters, or changes inside shared components are required. The optional Flutter SDK and iframe path are compatibility options, not the default integration.

## Describe the map

Edit the existing `.atlas/atlas.yaml`. Preserve the configuration page's `baseUrl`, `authentication`, and `roles` entries. Account IDs are stable UUIDs generated by the configuration page; do not replace them with usernames. Display names and tags may change without changing IDs.

Start with one reproducible route and expand once it captures correctly. Give each route page a stable `id`. Within one account, declare a route only once. Error messages, empty/populated content, and other in-page changes must not become additional nodes or navigation edges. Keep state preparation and checks in browser steps. Adapt this example to the app's real routes and accessible labels:

```yaml
routeMode: hash
profiles:
  phone: {width: 393, height: 852}
  tablet: {width: 1024, height: 768}
screens:
  - id: home
    title: Home
    route: /home
    prepare:
      - action: goto
        url: /#/home
    ready:
      all:
        - role: heading
          name: Home
        - role: button
          name: Open settings
  - id: settings
    title: Settings
    route: /settings
    ready: {role: heading, name: Settings}
edges:
  - id: open-settings
    source: home
    target: settings
    action: Open settings
    steps:
      - action: click
        target: {role: button, name: Open settings}
```

- Use `routeMode: pathname` for path-based routing. Match the real deployment path; do not guess routes from screen titles.
- `prepare` can use `goto`, `wait`, `fill`, and `click` to reach a deterministic state. Targets use an exact `role`/`name`, `kind: label`/`name`, or `kind: text`/`name`. A target must identify a unique element.
- Use `ready.all` to check body content as well as the route and heading. `ready.any` can contain complete alternative checks for valid content on the same route; this does not create separate pages. Include identity and state-specific evidence when accounts or samples differ. `not: {text: ...}` can exclude an error state; do not rely on an absence check alone.
- Omitted `screens[].roles` uses enabled accounts; use role tags to restrict a screen, or `roles: ['@anonymous']` for a shared signed-out screen. `{{role.username}}` can supply an identity check. Password templates are not supported and passwords must not appear in YAML.
- Declare real operations in `edges[].steps`. An edge from an anonymous page to an authenticated account page can use `steps: []` to invoke configured sign-in. Sign-out needs an explicit click on the app’s sign-out control. An ordinary edge without steps stays declared.
- Set `requireObservedEdges: true` when every declared transition must be verified for acceptance.

Use a trusted local MJS adapter only when the declarative steps cannot express the app's authentication or state preparation. Reference it through `adapterConfig`; adapter file paths are relative to the YAML file. Keep app-specific behavior in the target project's adapter, not in Atlas core.

## Capture and inspect

```sh
atlas build                     # All named profiles, or the default viewport
atlas view                      # First profile by default
atlas build --profile phone
atlas view --profile phone
```

Read the command summaries and generated `manifest.json` under `.atlas/generated/` (or its profile subdirectory). Confirm the intended account/route count and uniqueness, captured screens, edge statuses, and runtime errors. A declared edge is not a verified transition. `observed` requires an actual action followed by the expected route and ready content; a screenshot alone is insufficient.

Open the Viewer in a desktop browser and confirm the screenshots load. For catalog-based projects, select a captured page and use the live-session action. Atlas signs in and prepares the state in a separate Chrome context. Verify the selected account, page, and viewport through real operations, then close the session and check cleanup. A successful configuration-page login test does not prove page or navigation coverage.

After app changes, make sure its Web server serves the updated build before recapturing. A disk source fingerprint does not prove which build is loaded in the browser. Configuration or credential changes invalidate old capture snapshots for live sessions; recapture rather than reusing them.

If capture fails, inspect `latest-attempt.json` and the batch report. Atlas retains the previous successful map; its presence is not proof that the latest build passed. Report failures and unverified states explicitly. Do not mark states observed or bypass checks to complete a map.

## Local data

`atlas init` adds `/.atlas/` to the Flutter project's root `.gitignore`. Keep the entire directory local: YAML, credentials, private snapshots, sessions, screenshots, and layout artifacts. Credentials are stored as permission-restricted plaintext; never copy them into reports or shared examples. If tracked files or unsafe paths block initialization, explain the conflict without editing the Git index or untracking files automatically.

Google Chrome is the default browser channel. Local app URLs are allowed by default; remote development URLs require an intentional `allowRemoteUrls: true` setting. Use the app's actual address and accounts rather than importing another project's data or fixtures.

## Route identity guard

Atlas consumes a declared or observed route catalog; it does not infer Flutter router definitions from screenshots. Use the app's actual route table and browser URLs to construct the catalog. A screenshot variant is not a new route. For trusted adapters, provide a stable `accountId` when account display names can overlap or change; state must never be encoded as account identity. Discovery aliases changing observer IDs to the existing account/route node. A duplicate-route diagnostic requires fixing the catalog and recapturing, not hiding cards in the Viewer.

### Account workspaces and cache evidence

Standard YAML builds publish an application index with independent account/profile revisions. Show only one account workspace at a time; retain stable account UUIDs and one node per actual route. Public pages may share capture resources, but never expose another account's navigation in the current workspace.

Use `atlas build` for input-based reuse and `atlas build --force` when current runtime evidence is needed. Preserve capture IDs and timestamps on reuse. Never describe a cache hit as a new runtime verification. Use `atlas doctor` to diagnose Node, runtime dependencies, Viewer assets, installed Chrome, URL reachability, and source coverage. The package supplies Playwright, not the browser binary. Keep all private state under `.atlas/`; do not stage or commit it.

Use an explicitly declared `pageName` when the real page name is known. Fall back to the page title; never infer Dart class names from routes or screenshots.
