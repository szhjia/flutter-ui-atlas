## 行为变化与证据

| 项 | 行为 | 锚定测试 |
|---|---|---|
| 统一互斥 | `capture()` 与 `runDiscovery()` 共用 output 级锁 `.atlas-lock`（meta.json 含 pid/acquiredAt），整个批次持锁、finally 释放；活锁下两者在任何浏览器/适配器工作启动前即拒绝 | `tests/output-lock.test.mjs` 5 用例 |
| 陈旧自动接管 | 持有进程已退出 → 告警后接管重试；无 meta 空锁目录超 60 秒宽限 → 接管；宽限内视为他人正在获取 → 拒绝 | 同上（死 PID 用真实退出子进程、宽限用 utimes 控时） |
| 可行动拒绝文案 | 含锁绝对路径、持有 PID（可读时）与「删除该锁目录后重试」指引 | 同上（逐要素断言） |
| 旧锁兼容 | 旧 `.atlas-discovery-lock` 不再读取，残留可手工删除 | 协议文档声明 |

锁实现：`packages/capture/lock.mjs`（新增，仅依赖 Node 内建）；接入点 `packages/capture/discovery.mjs`（runDiscovery）与 `packages/capture/index.mjs`（capture 拆为持锁包装 + runCaptureBatch，批次体逐字未动）。

## 边界与说明

- 不强抢存活持有者的锁（活进程可能是交互式手动录制）；无 TTL 强抢选项（spec 裁决）。
- `process.kill(pid, 0)` 的 EPERM（进程存在但属其他用户）按存活处理，避免误抢。
- 未改 `publishBatch` 写序与原子性（附录 A 其余条目不在本模块）。
- 命令仍为裸 `pnpm` 执行（本机 rtk 缺失，见 failure-semantics 台账）；恢复后回到 `rtk proxy` 前缀。
